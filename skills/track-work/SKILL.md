# Track authorized coding work

Read `get_help` at `projects/tracking/prepare` for the live contract. Tool prefixes vary by harness; use the connected Kedeka server for the intended workspace.

1. Obtain the Git origin, branch and exact worktree. Remove credentials from the remote URL. Call `get_report` with `report: current_work` and `params: {session_key, repo, branch}`. Use the host's stable session identity; otherwise create one identifier once for this session. With active trusted hooks use their exact identity and `lifecycle_hooks: true`; without hooks follow the MCP protocol explicitly and do not claim automatic lifecycle tracking.
2. Resolve the repository's linked project and read its relevant briefs through `search_records` (`entity: brief`, `filters.repository`) and `get_record`. For large briefs read the outline, then the relevant sections. Keep their actual IDs and revisions. An unlinked repository must be linked to the intended project through Brief → Hubungkan agent; never substitute an unrelated repo, workspace or suggested task.
3. Search for a semantically matching task in that project. An authorized coding request includes finding or creating its task and tracking it; do not ask again merely for tracking. Reuse a matching task, or call `create_record` with `entity: agent_run`, a fresh `idempotency_key`, and `data: {task_title, task_description, repo, branch, worktree, session_key, briefs_read: [{id, revision}]}`. Use `task_id` instead of the title/description when a matching task exists. An empty brief list is valid only when the linked project has no briefs. On stale revisions, reread before retrying.
4. Continue an existing run only when its task scope, repository and branch match. Tell the user when resuming prior work. Do not take over another session unless authorized. When switching away from unfinished work, use `previous_task_status: keep` and record the previous results rather than implying completion.
5. Update affected project briefs with verified results before finishing; the coding request authorizes these related updates. Use the latest `base_revision`, exact section and a short note; reread and reconcile conflicts. Never invent tests or mark unperformed acceptance complete.
6. Finish through `update_record`, `entity: agent_run`, with its returned run ID and `data` containing `summary`, `verification`, current `briefs_read`, and any `commits` or `pull_request_url`. Set `task_status: done` after acceptance passes, `review` when external review remains, or send `event: pause` with the session key for unfinished work. A stopped process is not proof of completion. See `projects/tracking/finish` and `projects/tracking/hooks` for lifecycle details.

Tracking manages tasks, time and results. Execution permissions and workflow selection belong to the user and host independently of tracking; no skill, model or workflow whitelist is required. Track an already authorized child's work with its own real session identity, without duplicate runs; tracking itself neither requests nor forbids delegation.

Repair authentication or MCP discovery failures and report the exact blocker if unresolved. Respect disabled capabilities and host confirmation prompts. Do not claim tracking succeeded without a successful response. Hosts without hooks use explicit lifecycle calls and the server idle lease. Optional local adapters and activation instructions are in the repository README under “Hook lifecycle untuk coding agent”.
